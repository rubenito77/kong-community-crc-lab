## Diseño de credenciales

La API key fue generada dentro del pod Tekton. No se almacenó en Git, no se
recibió como parámetro y no fue escrita en logs ni evidencia. Los Steps la
compartieron mediante un `emptyDir` efímero; Kubernetes la conserva en
`Secret/demo-key-auth-credential` hasta realizar el rollback.

Recursos configurados:

```text
KongPlugin/demo-key-auth
KongConsumer/demo-key-auth-consumer
Secret/demo-key-auth-credential
Ingress/kong-transform-echo -> konghq.com/plugins=demo-key-auth
```

El Secret fue inspeccionado únicamente mediante metadatos:

```text
NAME                       TYPE     CREDENTIAL_TYPE
demo-key-auth-credential   Opaque   key-auth
```

No se registró el contenido de `.data.key`, dado que Base64 es reversible.

## Configuración validada

```yaml
plugin: key-auth
config:
  hide_credentials: true
  key_names:
    - apikey
```

El Consumer quedó programado correctamente:

```text
username: demo-key-auth-consumer
credentials: demo-key-auth-credential
status.conditions: Programmed=True
message: Object was successfully configured in Kong.
```

## Comparación

| Caso | `/transform` | Resultado |
|---|---:|---|
| Línea base, sin plugin | 200 | Upstream accesible sin credencial. |
| Sin `apikey` | 401 | Kong rechazó la solicitud. |
| `apikey` inválida | 401 | Kong rechazó la solicitud. |
| `apikey` válida | 200 | Consumer autenticado. |

| `/demo` y `/demo2` | 200 | Rutas de control aisladas. |

## Validación externa sin credencial

```text
HTTP/1.1 401 Unauthorized
x-kong-response-latency: 0
server: kong/3.9.3
```

```json
{
  "message": "No API key found in request"
}
```

La ausencia de `x-kong-upstream-latency` y la latencia de respuesta de Kong en
cero confirman que la solicitud sin credencial fue rechazada antes del backend.

## Reconciliación

La búsqueda de `error|failed|invalid|rejected` en los logs recientes del Kong
Ingress Controller no devolvió resultados.

## Rollback ejecutado

```powershell
oc annotate ingress kong-transform-echo -n kong-demo konghq.com/plugins-
oc delete kongplugin demo-key-auth -n kong-demo
oc delete kongconsumer demo-key-auth-consumer -n kong-demo
oc delete secret demo-key-auth-credential -n kong-demo
```

Después del rollback, `/transform` debe volver a HTTP 200 sin requerir el
header `apikey`; `/demo` y `/demo2` deben permanecer en 200.

El rollback fue ejecutado y validado el 2026-08-26:

```text
KongPlugin/demo-key-auth: NotFound
KongConsumer/demo-key-auth-consumer: NotFound
Secret/demo-key-auth-credential: NotFound
Ingress/kong-transform-echo plugins: vacío
/transform: HTTP 200
/demo: HTTP 200
/demo2: HTTP 200
x-kong-upstream-latency: 2
x-kong-proxy-latency: 1
errores recientes de KIC: ninguno
```

La presencia de `x-kong-upstream-latency` confirma que `/transform` volvió a
alcanzar el backend sin autenticación. La credencial dejó de existir en el
cluster al eliminar el Secret.

## Conclusión

P03-01 queda aprobada y revertida. Kong autenticó correctamente al Consumer mediante una
API key gestionada como Secret, rechazó credenciales ausentes o inválidas,
ocultó la credencial al upstream y mantuvo aisladas las demás rutas.
